# 문항 내용 정규화·해시 규칙 v1

작성: Codex · 2026-08-24
상태: **설계안 · 구현 전**
식별자: `normalized_item_content.v1`
용도: `item_analysis_registry.json`의 `content_hash`

> 이 문서는 `item_axes` 레코드가 판정 당시의 문항 내용과 여전히 같은지 검사하기 위한 정본이다. 구현·backfill을 승인하지 않으며 기존 D1 해시를 변경하지 않는다.

---

## 1. 기존 D1 해시와 구분

`normalized_item_content.v1`은 `item_analysis_registry.json`의 내용 검증용 해시 기준이다. 기존 D1 `user_items.content_hash`의 `qnorm.v1`과 이름·목적·정규화 규칙이 다르다.

- D1 `qnorm.v1`: 기존 투입 멱등·중복 처리 경로
- `normalized_item_content.v1`: `item_axes` 재판정 필요 여부 확인

`content_hash.basis`가 정확히 `normalized_item_content.v1`이 아니면 이 레지스트리의 검증값으로 대체 사용하지 않는다. 기존 D1 해시를 재계산하거나 바꾸지 않는다.

---

## 2. 해시에 포함하는 필드

아래 네 값을 순서대로 사용한다.

```text
1 unit_id
2 question_text
3 answer
4 explanation
```

- `question_text`는 필수이며 정규화 결과가 빈 문자열이면 해시를 만들지 않는다.
- 나머지 필드는 실제 값이 없으면 `null`로 둔다. `null`과 빈 문자열 `""`을 합치지 않는다.
- `question_no`는 배치가 바뀔 수 있으므로 제외한다.
- `user_item_id`는 레코드 기본키이므로 제외한다.
- `problem_type_id`는 legacy 호환 식별자이고 축 생성의 순환을 만들 수 있으므로 제외한다.
- `type_name`은 유형 지정 전에는 대부분 null이며, 이후 유형 지정만으로 축 판정 근거가 바뀌지 않으므로 제외한다.
- `difficulty`는 학생 정답률 등에 따라 달라질 수 있고 축 판정 근거가 아니므로 제외한다.
- `concept_ids`, `item_axes`, 판정자, 판정 시각은 분석 결과·메타데이터이므로 제외한다.
- 축 판정 근거는 `question_text`, `answer`, `explanation`뿐이며, `unit_id`는 단원 경계를 보존하기 위한 문맥값이다.

QF의 문제 본문·정답·해설 중 하나가 교정되면 이 해시가 달라져 재판정 대상으로 잡힌다. 이후 유형 지정이나 정답률 기반 난도 갱신만으로는 해시가 달라지지 않는다.

### 2.1 그림 정보의 현재 확인 범위와 한계

판정용 `B_axis_blind_items_180.v1.csv`에서는 180건 중 110건의 `question_text`에 리터럴 `그림 정보:`가 포함된 것이 확인됐다. 원의 성질 D1 투입용 JSON도 그림 서술을 `question_text` 내부에 포함하며, 워커 bulk 경로는 입력 `question_text`를 trim한 뒤 그대로 `user_items.question_text`에 저장한다.

사용자가 라이브 D1에서 단원 전체를 조회한 결과는 다음과 같다.

```text
unit_id      M3_CIRCLE_PROPERTIES
total        2168
with_figure  1084   question_text LIKE '%그림 정보:%'
with_word    2122   question_text LIKE '%그림%'
현재 판정    부분 확인
```

`total=2168`은 확정 등록 수와 일치해 조회 센티널을 통과했다. 따라서 D1 `question_text`에 그림 서술이 실제 저장된 경로는 실측으로 확인됐다. `with_word=2122`는 “다음 그림에서” 같은 상용구까지 포함하므로 그림 서술 포함 여부의 지표로 사용하지 않는다.

그러나 `with_figure=1084`는 전체의 정확히 절반이다. 판정 대상 180건에서는 110건(61.1%)에 그림 서술이 있고 70건에는 없다. 그림 서술이 없는 70건 중 29건에서 당시 `AXC01`이 판정됐다. 판정 112차에서 이를 대체한 `AXC01_lines`, `AXC01_vertex`, `AXC01_tangent_count`도 그림을 봐야 아는 축이므로 이 범위는 그림만 교정될 때 v1 해시가 바뀌지 않는다.

따라서 다음처럼 범위를 구분한다.

- D1 `question_text`에 판정에 충분한 그림 서술이 있으면 v1 해시가 그 서술 변경을 감지한다.
- 그림 서술이 없거나 불충분하고 축 근거가 실제 그림뿐이면 v1 해시가 그림 변경을 감지하지 못한다.
- D1 전체의 정확한 1/2과 판정 표본의 61.1%가 다른 원인은 현재 조사하지 않는다. 어느 경우에도 “구멍 없음”이라는 결론은 성립하지 않는다.
- `normalized_item_content.v2`의 **예정 항목**으로 안정된 그림 내용 해시를 등재한다. 안정된 그림 원본 필드가 계약에 없으므로 지금 v2를 만들거나 구현하지 않는다.
- v1은 소급 변경하지 않으며, v2가 생기기 전에는 `AXC01_lines`, `AXC01_vertex`, `AXC01_tangent_count`의 재판정 필요 여부를 `content_hash` 일치만으로 종결하지 않는다.

## 3. 문자열 정규화

각 비-null 문자열에 다음 순서를 적용한다.

1. 입력을 유니코드 문자열로 읽는다.
2. 유니코드 정규화는 **NFC**만 적용한다. NFKC·NFKD 같은 호환 정규화는 사용하지 않는다.
3. CRLF와 CR을 LF로 바꾼다.
4. LF를 포함한 연속 유니코드 공백을 ASCII 공백 U+0020 하나로 바꾼다.
5. 문자열 앞뒤의 U+0020을 제거한다.
6. 대소문자, 숫자, 수학 기호, 문장부호는 변환하지 않는다.

따라서 줄바꿈·탭·연속 공백 차이는 흡수하지만, 어휘·수식·조판 기호 차이는 보존한다.

### 3.1 반드시 보존하는 조판 구분

```text
˚  U+02DA MODIFIER LETTER RING ABOVE
°  U+00B0 DEGREE SIGN
```

두 문자는 서로 변환하지 않는다. 특히 유형명에 쓰인 `˚`(U+02DA)를 `°`(U+00B0)로 고치지 않는다. NFC에서는 둘이 서로 같은 문자가 되지 않으며 정규화 결과와 해시도 달라야 한다.

다음 호환 변환도 하지 않는다.

```text
전각 문자 ↔ ASCII
² ↔ ^2 또는 2
× · ↔ *
− – ↔ -
˚ ↔ °
```

이 제한 때문에 이 규칙은 NFKC를 사용하는 기존 `qnorm.v1`과 호환되지 않는다. 두 basis를 섞지 않는다.

## 4. 정규화 예시

| 입력 | 정규화 결과 |
|---|---|
| `"  A\tB\r\nC  "` | `"A B C"` |
| `"x  +  1"` | `"x + 1"` |
| `"˚"` | `"˚"`(U+02DA) |
| `"°"` | `"°"`(U+00B0) |
| `"ＡＢＣ"` | `"ＡＢＣ"` |
| `"x²"` | `"x²"` |
| `null` | `null` |
| `""` | `""` |

`˚`와 `°`, `null`과 빈 문자열은 각각 다른 정규화 결과다.

## 5. 바이트 직렬화

구현 언어별 JSON 이스케이프 차이를 피하기 위해 JSON 문자열 자체를 해시하지 않는다. 다음 길이 접두 형식으로 바이트를 만든다.

```text
ASCII "normalized_item_content.v1" + 0x00
각 필드 4개를 §2 순서로 반복:
  null   -> 0xFFFFFFFF (부호 없는 32비트 big-endian)
  string -> UTF-8 바이트 길이(부호 없는 32비트 big-endian)
            + 정규화 문자열의 UTF-8 바이트
```

- UTF-8에는 BOM을 붙이지 않는다.
- 길이는 문자의 개수가 아니라 UTF-8 바이트 수다.
- 필드 이름은 직렬화하지 않는다. 순서는 §2로 고정한다.
- 문자열 길이가 `0xFFFFFFFE`를 넘으면 입력 오류로 처리한다.

최종 `content_hash.value`는 위 전체 바이트열의 SHA-256을 계산한 소문자 64자리 16진수다.

## 6. `content_hash` 계약

```json
{
  "algorithm": "sha256",
  "value": "64자리 소문자 16진수",
  "basis": "normalized_item_content.v1"
}
```

다음이면 재판정 대상이다.

- 현재 문항으로 계산한 값과 저장된 `content_hash.value`가 다름
- `basis`가 다름
- basis 판본의 정규화 규칙이 바뀜

단, 이 조건은 v1 basis가 실제 판정 근거를 포함하는 축에만 충분하다. 그림 서술이 `question_text`에 없는 `AXC01_lines`, `AXC01_vertex`, `AXC01_tangent_count`는 동일한 v1 해시만으로 재판정 불필요를 확정할 수 없다. 축별 재판정 범위는 `B_item_axes_schema.v1.md`의 명세 계약을 따른다.

v1 규칙을 수정해야 하면 같은 식별자를 덮어쓰지 않고 `normalized_item_content.v2`를 만든다. 과거 레코드는 당시 basis와 함께 보존한다.

---

## 7. 구현 전 필수 시험 벡터

구현 시에는 최소한 다음 불변식을 자동 시험해야 한다. 지금은 시험 코드나 검증기를 만들지 않는다.

1. CRLF·CR·LF와 탭·연속 공백 변형이 같은 정규화 결과를 낸다.
2. NFC로 동등한 문자열은 같은 결과를 낸다.
3. `˚`(U+02DA)와 `°`(U+00B0)는 다른 결과와 다른 해시를 낸다.
4. `null`과 `""`는 다른 바이트열과 다른 해시를 낸다.
5. 필드 경계가 다른 입력은 이어 붙인 표시가 같아 보여도 다른 해시를 낸다.
6. 같은 입력은 구현 언어와 운영체제에 관계없이 같은 UTF-8 바이트열을 만든다.

이 문서는 설계 정본이며 승인 전 구현·기존 해시 변경·D1 backfill을 하지 않는다.
