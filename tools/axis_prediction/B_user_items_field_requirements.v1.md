# user_items 필드 요구사항 확정 (매칭용) v1 (2026-08-11)

> 검수 지시(매칭설계 1번): user_items 필드 요구사항 확정. q_norm 저장 vs 실시간 계산, 규칙 변경 시 재생성, 정규화 규칙 버전 병기 여부(axis_map_version 선례) 검토.
> 임계값 선행 확정: 0.99(텍스트 체제). [[B_match_threshold_experiment.v1.md]]
> **검수 승인(2026-08-11): ① norm_rule_version 각인 승인 · ② 실시간 계산 승인(전환기준 명시 조건) · ③ 대량투입 전 PDF·이미지 실측 게이트.** 스키마 v3(norm_rule_version)는 실측 통과 후 착수(순서조정).

## 결론 (TL;DR)
- **user_items 스키마 v2 그대로 충분. 신규 컬럼 0.**
- 매칭 키 = `question_text`(원문) + `problem_type_id`(+ `unit_id` 후보축소). 셋 다 이미 존재.
- **q_norm 저장하지 않음 → 진단 시 런타임 계산.**
- 정규화/매칭 규칙 버전은 **user_items가 아니라 매칭 결과(진단 레코드/attempts)에 각인**(axis_map_version 선례).
- similarity·숫자시퀀스·2위 마진 = 전부 question_text에서 런타임 파생 → 저장 불요.

## 근거 1: 매칭 흐름 ↔ 필드 매핑
매칭 규칙(검수 확정): ① unit_id·problem_type_id 후보축소 → ② 정규화 유사도 ≥0.99 → ③ 통과 2개↑ 미매칭 → 미달 AI폴백.

| 매칭 단계 | 필요 데이터 | user_items 필드 | 상태 |
|---|---|---|---|
| ① 후보축소 | unit_id, problem_type_id | `unit_id`, `problem_type_id` | ✅ 있음 (idx_ui_unit·idx_ui_type) |
| ② 유사도/숫자 | 원문 텍스트 | `question_text` (NOT NULL) | ✅ 있음 |
| ③ 마진 판정 | 후보 간 점수 | (런타임 계산) | 저장 불요 |

→ 매칭에 **저장이 필요한 필드는 이미 100% 존재.** 스키마 변경 없음.

## 근거 2: q_norm 저장 vs 런타임 계산 (검수 3항목 판정)
- (a) 저장 vs 실시간 → **실시간(런타임) 권장**
- (b) 저장 시 규칙 변경마다 재생성 → **바로 이것이 저장 안 하는 결정적 이유**
- (c) 정규화 규칙 버전 병기 → **user_items엔 불요. 매칭 결과에 각인**

이유:
1. **후보집합이 작다.** unit+type로 좁히면 한 유형당 수~수십 건. 짧은 문자열 몇 개 정규화는 무시할 비용. "저장하면 조회 빠름"의 이점이 실효 없음 — 풀스캔이 아니라 인덱스로 좁힌 소집합 비교라서.
2. **규칙이 아직 안정 안 됨.** 이번 세션만 해도 지수 통일·어휘금지로 정규화/전사 이해가 계속 바뀌었다(0.873→1.0). 저장 q_norm은 규칙 바뀔 때마다 전 항목 재생성 필요 + **드리프트 위험**: 구 규칙으로 저장된 q_norm ↔ 신 규칙으로 정규화된 진단 질의 → 조용한 미스매치(오매칭 금지 원칙 위배). 런타임 계산은 규칙이 바뀌어도 재생성 0.
3. **단일 진실원.** question_text 원문 하나만 저장하면 정규화는 항상 현재 규칙으로 일관 재생성.

## ② 실시간 → 저장(q_norm) 전환 기준 (검수 승인, 2026-08-11)
지금은 실시간. **아래 트리거가 오면 스키마 v3로 q_norm 컬럼 추가.**
- **정성(1차 트리거)**: 진단 응답에서 매칭 단계 지연 체감(analyze 응답에 매칭이 유의미 지연 추가).
- **정량**: 단일 `(unit_id, problem_type_id)` **후보가 지속적으로 수백 건↑**. — ★이게 실질 비용 동인. 매칭이 항상 unit+type로 좁히므로 후보집합 크기는 **총 등록건수와 무관**하게 결정됨.
- **총건수 5,000 초과** = 검수 제시 기준. 위 후보-집합 기준과 함께 **재검토 시점 트리거**로 채택(총건이 커지면 특정 유형에 수백 건 쏠릴 확률↑이라 점검). 단 narrowing이 유지되면 5,000 자체로 느려지진 않음 — 그래서 지금 컬럼 불필요, 근거 생기면 v3.
- **전환 시 조치**: user_items에 `q_norm` + `qnorm_version` 컬럼. 등록/수정 시 계산·저장. 규칙 변경 시 `WHERE qnorm_version != 현재`로 대상만 재생성(①의 레코드 각인과 동일 원리 = "어느 레코드 재계산할지 질의로 거른다").

## 근거 3: 정규화 규칙 = canonical 버전 동결 (구현 4번의 조건)
- 현재 norm 함수가 **ocr_measure.html·match_lab.html·실험 perl에 각각 중복** 존재. 매칭 구현(4번)에서 워커가 또 자기 사본을 가지면 **드리프트 위험**(도구·워커가 다른 정규화 → 판정 불일치).
- ⇒ 정규화 규칙을 **하나의 canonical 스펙으로 명문화 + 버전 태그**(`qnorm.v1`). 워커 매처·클라 도구가 같은 스펙 참조. 규칙 변경 시에만 버전 올림.
- 이 버전 문자열을 **매칭 결과(attempts/진단 레코드)에 각인** → "왜 매칭/미매칭했나" 감사 가능(axis_map_version과 동형). user_items 행에는 넣지 않음(항목엔 정규화 산물을 안 담으므로 각인할 대상이 없음).
- 현재 규칙(=qnorm.v1 후보): NFKC → 공백제거 → `^`제거 → `×·`→`*` → `−–`→`-` → `.,·、。`제거 → 소문자화. (NFKC가 `²→2` 등 상첨자 이미 처리.)

## 근거 4: pending 항목
- status=pending(problem_type_id 없음)은 매칭 후보 제외. 매칭 질의 = `WHERE status='approved' AND unit_id=? AND problem_type_id=?`. 기존 인덱스로 커버. 스키마 영향 없음.

## 텍스트 vs 이미지 회귀 (검수 주의 반영)
- 0.99 확정은 **텍스트 입력 기준**. 이미지·PDF OCR은 드리프트 재등장 가능 → 같은문항 1.0 미달·다른문항 상승으로 겹침 재발 가능.
- ★**필드 결정은 두 체제 모두에 안정**: 이미지 체제에서 복합규칙(숫자시퀀스 정확일치 + 유사도 + 타입필터 + 마진)으로 가더라도 그 성분들이 **전부 question_text 런타임 파생** → 저장 필드 변화 0.
- ⇒ **필드 스펙은 지금 확정 가능.** 임계/규칙 세부는 이미지 실측 후 조정하되 스키마는 불변.

## 스키마 v3 결정 (2026-08-11, 검수 #3 "소급 불가" 지적 → 코드 확인)
원칙: **입력 테이블은 참조, 결과 테이블은 각인.** 단 예외 = **소급 불가능한 것(그 순간의 판독 산출물)**은 입력 테이블이라도 남겨야 함.
- 코드 확인(worker `itemAdd` 308-328, `itemStructure` 254-306): user_items는 **판독기 식별 필드 없음**(`source_note`=자유메모뿐), `/structure`의 `raw_text`(교사 원문)는 구조화 후 **`/add`에 안 넘어가 미보관**. 학생측 Fix-A와 비대칭.
- ⇒ **스텝2 = 삭제 아님, 교체**: `norm_rule_version`(→결과레코드, 4번)이 아니라 **비소급 2필드를 대량투입 전 추가**:
  - `source_text`(nullable): AI 구조화 이전 원문(교사 붙여넣기/투입 소스). Fix-A 문항판. 재구조화 시 PDF 재탐색 불요.
  - `provenance`(nullable, JSON 또는 문자열): 판독기 이력 `{ingest: admin|bulk, extraction: worker-<VERSION>|gpt-<...>|manual, at}`. 나중에 버그 판독기 산출물 격리 가능(재판독 복구의 전제).
  - 둘 다 nullable·가산 → 안전. **비소급이라 투입 후엔 회복 불가 = 순서상 반드시 투입 전.**
- norm_rule_version은 그대로 **결과레코드(attempts) 각인**(4번). concept 매핑 버전도 같은 자리(아래).

## 대량투입/매칭 다운스트림 원칙 (검수 #2·#4 반영)
- **미매칭=판독오류 무료탐지기(#2)**: PDF실측서 0.99미달 3건 = 판독오독 3건(동일). ⇒ 매칭 구현(4번)에 **0.99미달 건을 사유와 함께 로그** → ISSUE 판독빈도 실측이 자동 축적. 미매칭률 = 판독품질 상시지표.
- **/add-bulk 멱등성(#4a)**: 중복키 = `unit_id + problem_type_id + 정규화본문 해시`(번호 아님, §매칭 번호배제와 동일 이유). 등록 시점에 매칭 정규화 재사용. 중복문항은 "후보 여럿→미매칭"으로 미매칭률 조용히 올리므로 차단 필수. **부분실패 표(성공n/실패목록+사유)를 admin 화면에** — 롤백보다 재실행(멱등)이 우선.
- **concept_ids 조인-not-스냅샷(#4b)**: 매핑 `problem_type_id→concept_ids`가 아직 이동 가능(Tier2 미완) → user_items에 **스냅샷 저장 대신 런타임 조인**. 매핑 테이블에 버전, 진단 결과레코드에 사용 매핑버전 각인(norm_rule_version과 동일 원리). ★현재 `/structure`는 스냅샷(300행 concept_ids 상속)이라 이 결정 채택 시 동작 변경.
