# 매칭 통합 설계 — 진단 파이프라인 삽입 지점 (착수 전 검수 판정) v1 (2026-08-14)

> 검수 "착수 전 확인 1건": 매칭이 진단 경로 어디에 들어가는가. §8대로 파이프라인 [코드확인] 후 옵션·트레이드오프 제시.
> ★확정 전 매칭 구현 없음.

## 1. 파이프라인 실측 [코드확인] (`runStagedEngineAdapter` 1201~)
- **stage-1**(1207, 1콜) `UNIT_ASSIGN_SCHEMA`(822): 문항 → `question_no`·`unit_id`·`response_status`. ★**question_text 없음.**
- **stage-2**(1233, 단원별 1콜씩·병렬) `assignTypesForUnit`(946): 시험지를 읽어 **① question_text 전사 · ② observed_error_tags(학생 오류 관측)·student_work_text · ③ 유형 분류**(범주 2단계 enum, `TYPE_ASSIGN_SCHEMA` 844, 유형 87~1131종). 셋이 **한 콜에 엮임**.
- **매칭 원설계**(주석 862): stage-2가 낸 question_text로 "등록 문항(user_items)과 대조해 **정답/해설을 붙인다**". = **매칭은 원래 stage-2 이후 답/해설 첨부 단계**. 유형은 stage-2(AI)가 정함.

## 2. ★검수 비용 가설 정정 (코드 근거)
검수: "stage-2가 최대 비용 → 매칭을 앞에 두고 매칭 성공 건은 stage-2 제외하면 비용↓." 그러나:
- **매칭엔 question_text 필요 = 시험지를 읽어야 함.** stage-1은 본문을 안 내므로, 매칭을 stage-2 앞에 두려면 어딘가서 전사(=시험지 vision read)를 해야 한다.
- **매칭돼도 학생 오류 관측(observed_error_tags·student_work_text)은 여전히 AI가 시험지를 읽어야** 한다(등록 문항은 "정답/해설/유형"을 주지, "이 학생이 무엇을 틀렸나"는 안 준다). = stage-2의 file-read·오류관측은 매칭 성공해도 못 건너뜀.
- 절감 가능한 것은 **유형 enum(수백 종) 부분뿐** — 이건 schema/prompt 토큰. 그러나 **vision 입력(시험지 페이지)이 콜당 대부분 비용**이라, enum 제거의 순절감은 불확실(미측정). 50문항 $2.5의 stage별 분해 없음.
- ⇒ **"매칭으로 stage-2 생략 = 비용↓"은 코드상 성립 안 함**(전사·오류관측이 남음). 매칭의 확실한 가치는 **정확도**(사람 확정 유형이 AI 붕괴 유형 90%를 대체) + **답/해설 첨부**.

## 3. 통합 옵션
- **옵션 2 (권장·저위험) — stage-2 이후 매칭**: stage-2 그대로 → question_text로 user_items 대조(unit+qnorm.v1 유사도 ≥0.99) → **매칭 성공 시 problem_type_id를 등록 문항 유형으로 덮어씀**(AI 붕괴 유형 교정) + **답/해설 첨부**. 미달·후보다수 → 미매칭(stage-2 유형 유지) → AI폴백. 파이프라인 무재구성. 원설계(주석 862)의 연장. **비용 불변·정확도↑.**
- **옵션 1 (비용 최적화·보류) — 매칭 선행 + 유형 enum 스킵**: question_text 전사를 stage-1로 이동 → 매칭 → 매칭 성공 건은 stage-2를 **유형 enum 없는 축소 스키마**(오류관측만·유형은 매칭값)로 호출. 미매칭만 full stage-2. ★절감은 enum 토큰뿐이고 **미매칭 건은 시험지를 두 번 읽을 위험**(stage-1 전사 + stage-2 오류관측) → 순절감 매치율 의존·불확실. 재구성 큼. **측정 후 결정.**
- **옵션 3 — 매칭은 답/해설만, 유형은 AI 유지**: 원설계 그대로. 유형 붕괴 90% 미교정 → 정확도 이득 작음. 비권장.

## 4. 권장
1. **옵션 2 먼저**: 매칭 post-stage-2로 (a) 유형 교정 (b) 답/해설 첨부 (c) 0.99미달 로그(판독오류 상시지표). = 90% 붕괴 문제를 등록 문항 범위에서 해소하는 확실한 이득, 저위험.
2. **stage별 비용 실측**(usageSink 분해: stage-1 vs stage-2, enum 토큰 비중)을 별도로 → 그 결과로 옵션 1(enum 스킵) 착수 여부 판정. **비용 최적화는 측정 없이 하지 않음**(effort/품질 직결 원칙과 동일).

## 5. 매칭 공통 확정(검수) — 옵션 무관
- 1차 축소 `unit_id`(problem_type_id 보조, 유형 흔들림 90% 감안) · 2차 qnorm.v1 유사도 ≥0.99 · 후보 다수 → 미매칭 → AI폴백(오매칭>미매칭) · `norm_rule_version`(=qnorm.v1) 결과레코드 각인 · 0.99미달 사유 로그 · **후보 = status='approved'만**(pending·archived 제외).
- 매칭 대상 풀 = user_items(등록 문항). (d)+3단으로 approved된 것만 → 풀이 커질수록 매칭률↑.

## 6. 검수 판정 요청 = 1건
**통합 지점 = 옵션 2(post-stage-2, 정확도 우선·비용 불변) 승인?** + stage별 비용 실측을 옵션1의 선행조건으로 두는 데 동의?
→ 승인 시: 매칭 함수(qnorm.v1 dice·후보조회·0.99게이트·유형덮어쓰기·답해설첨부·미달로그)를 runStagedEngineAdapter의 stage-2 직후에 삽입 + 결과레코드 norm_rule_version 각인. 확정 전 구현 없음.
