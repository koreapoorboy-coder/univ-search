# 배선 ③ — 학생 식별자 체계 조사 (2026-08-09)

> ④ 판정: `observed_axes` = **누적 프로파일**(교사 학기조회). "이 학생은 C3에서 반복 무너짐"은 **여러 시험을 학생 단위로 묶어야** 나옴. 지금은 한 시험지 스냅샷(예: C3·2, C2·2, C4·1)에 그침. **누적의 전제 = 안정적 학생 신원 + 저장**. 이 조사는 실태 + 운용안. (구현 아님, 방향 제안.)

## 1) 현재 식별 수단 — 자유텍스트 이름뿐
- 입력: `index.html`·`hybrid.html:134` `<input id="student_name">` "학생 이름 *"(필수, placeholder "예: 김OO").
- 흐름: payload `student_profile.student_name`(worker `:1125`도 이 값만 읽음). 용도 = **리포트 표시용**. 그 외 부수 필드 `gradeLabel`·`course`(학년·과정 라벨)도 자유입력.
- ❌ **안정적 `student_id` 없음.** 이름 문자열이 유일 키.
  - 동명이인(김민수 2명) 충돌 / 오타·띄어쓰기로 신원 분기("김민수"≠"김 민수") / 개명 시 이력 단절. **누적 키로 부적합.**

## 2) 저장소 실태 — 전 구간 무상태(persist 0)
- **클라이언트**: `localStorage`는 **Worker URL만** 저장(`math_ai_bridge_client.js`·`hybrid.html` STORAGE_KEY). 진단 결과·학생데이터 저장 **안 함**. "URL 저장" 버튼도 주소용.
- **서버(Worker)**: `wrangler.toml`에 **KV·D1·R2·Durable Objects 바인딩 전무**. Worker는 무상태 — 처리 후 업로드파일 삭제(`deleteUploadedFiles`), 결과 반환 후 소멸.
- **결과 영속 없음**: 진단(observed_axes·triggered_rules·tags)은 브라우저에서 1회 렌더(인쇄/PDF 가능)뿐, **학생 키로 저장되는 곳 0**. 페이지 새로고침이면 사라짐.
- ⇒ **매 시험 = 독립 1회성 스냅샷.** 누적 인프라가 아예 없음.

## 3) 누적 경로 — 필요한 4요소(현재 0/4)
observed_axes를 학생 단위로 누적해 "반복 취약축"을 뽑으려면 모두 필요:
- (a) **안정적 학생 키** — 현 자유이름 대체(§1 문제).
- (b) **저장소** — 그 키로 색인되는 store(§2 전무).
- (c) **쓰기 단계** — 진단마다 `{student_key, date, exam_scope, observed_axes}` 를 append. (현재 진단은 반환만 하고 버림.)
- (d) **집계 뷰** — 학생의 여러 레코드 across observed_axes 합산→"C3 반복" 표면화. (미존재.)
- **넷 다 신규.** 축 배선 자체(재태깅→오버레이→Worker→observed_axes)는 완성됐으나, **그 산출을 담을 그릇이 없음**이 실가치의 병목.

## 4) 실무 운용안 (제안 — 택1 또는 A→B 단계화)
전제 제약: 엔진은 클라이언트, Worker 무상태, **교사 운용·사용자 명령줄 불가**(무설치 지향).

### 핵심 선결 = 안정적 학생 키 (공통·최우선)
- 자유이름 대신 **교사배정 학생코드**(반+번호 or 로스터ID, 예 `2-3-14`)를 이름과 함께 입력. 최소 변경·최대효과. 동명이인·개명·오타 내성.
- 대안: `이름+학년+생년4자리` 복합키(코드체계 없을 때). 코드보다 약함.

### Option A — 교사 로컬(무백엔드, 지금 착수 가능)
- 누적을 **브라우저 localStorage/IndexedDB**(교사 기기)에 `student_key→[records]` 로 저장. 또는 **학생별 JSON 파일 export/import**(교사가 보관, 다음 시험 때 불러와 append).
- 장점: 인프라 0·즉시. 단점: 기기 종속·교사간 공유 안 됨·기기 바뀌면 유실(파일 export로 완화).

### Option B — Cloudflare 백엔드(견고, 확대용)
- Worker에 **KV 또는 D1 바인딩** 추가 + 신규 엔드포인트 `POST /record`(append) · `GET /profile?student_key=`(집계). 
- 장점: 교차기기·영속·교사간 공유. 단점: 바인딩 설정·배포·학생키 스킴 운영 필요. 개인정보(이름) 저장이면 보관·동의 고려.

### 권장: A로 시작(학생키 스킴 확정 + 로컬누적) → 스키마를 B로 이관 설계
- 지금 가장 높은 레버리지 = **학생키 스킴 도입**(자유이름→코드). 이거만 해도 이후 A/B 어느 쪽이든 누적이 성립.
- observed_axes 레코드 형태 초안: `{student_key, date, exam_label, scope_units:[], axes:{C1..E3: {total,wrong}}}`. §3(c)(d)의 최소 단위.
